# PokeRL — A Benchmark Study of Reinforcement Learning for Pokémon Battles

Reinforcement learning agents for competitive Pokémon singles battles (`gen9randombattle`) on
a local [Pokémon Showdown](https://github.com/smogon/pokemon-showdown) server, via
[poke-env](https://github.com/hsahovic/poke-env).

The project is a **controlled benchmark study**, not a single agent. It compares five learning
algorithms across four independently varied experimental axes, with three seeds per cell and a
fixed evaluation protocol, so that differences between arms are attributable to the thing that
was varied.

---

## Research questions

| Axis | Question | Cells |
|---|---|---|
| **A. Algorithm** | Which RL family suits a partially-observable, stochastic, discrete-action battle? | tabular Q-learning, DQN, A2C, PPO, PPO+masking |
| **B. State encoding** | How much does a rich state representation buy over the 12-feature encoding used in prior work? | `v0` (12 features) vs `v1` (289 features) |
| **C. Reward shaping** | Does dense potential-based shaping beat a sparse win/loss signal? | `sparse`, `shaped`, `aggressive` |
| **D. Training opponent** | Does training against varied opposition generalise better than a single opponent? | `random`, `max_power`, `heuristic`, `mixed` |

Every cell varies **exactly one field** from the reference cell (masked PPO, `v0`, `shaped`,
vs `heuristic`) — enforced by construction in [scripts/gen_configs.py](scripts/gen_configs.py)
rather than by hand-editing YAML.

## Relationship to prior work

| Repo | What it is | How this project relates |
|---|---|---|
| [leolellisr/poke_RL](https://github.com/leolellisr/poke_RL) | Battle RL on Showdown; paper *"I Choose You, Reinforcement Learning!"* (SBGames 2024) | **Conceptual reference.** Its 12-feature encoding is reproduced exactly as `v0`, so `v0` results are comparable. Its code targets Keras-rl and poke-env's removed `EnvPlayer` API and does not run against poke-env 0.15. |
| [reddheeraj/PokemonRL](https://github.com/reddheeraj/PokemonRL) | PPO on **Pokémon Red** via the PyBoy emulator — overworld navigation from pixels | **Not battle RL.** Different problem entirely; not used. |

The `v0` encoder is also the encoding in poke-env's own official example, which this project
uses as its known-good foundation before building on top.

## Setup

Requires **Python ≥ 3.10** and **Node.js ≥ 18**. Verified on Python 3.13.2 / Node 22.14.

```powershell
# 1. Python environment
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install -e .

# 2. Pokémon Showdown server (one-time; clones and npm-installs into pokemon-showdown/)
.\scripts\setup_showdown.ps1

# 3. Start the server — leave this running in its own terminal
.\scripts\start_showdown.ps1
```

`--no-security` disables rate limiting and authentication. Without it, parallel training
environments get throttled into connection timeouts. **Only ever expose this server on
localhost.**

Verify the whole pipeline before training anything:

```powershell
.\.venv\Scripts\python.exe -m pokerl.smoke_test
```

This checks that battles run to completion, that both encoders emit correctly-shaped,
in-range, NaN-free vectors, and that the Gym env resets and steps under a legal masked action.

## Running experiments

```powershell
# Generate the experiment matrix (11 configs)
.\.venv\Scripts\python.exe scripts\gen_configs.py

# Full study: 11 cells x 3 seeds, then evaluation, cross-evaluation, and figures
.\scripts\run_all.ps1

.\.venv\Scripts\python.exe -m pokerl.train    --config configs\exp\ppo_masked_v0.yaml --seed 0
.\.venv\Scripts\python.exe -m pokerl.evaluate --run results\ppo_masked_v0_seed0
```

Training curves: `tensorboard --logdir results`.

## Evaluation protocol

Identical for every agent — anything varying between arms other than the trained policy would
confound the comparison.

- **500 battles** against each of three fixed baselines: `RandomPlayer`, `MaxBasePowerPlayer`,
  `SimpleHeuristicsPlayer`
- **3 seeds** per cell; results reported as mean ± std
- **Deterministic** action selection at evaluation
- **Cross-evaluation**: a pairwise matrix in which trained agents also fight *each other*

Reported win rates are computed from the *opponent's* loss counter, since poke-env's player
counters accumulate across successive opponents.

## Results

Generated by `scripts\analyse.py` — every figure regenerates from the committed CSVs alone,
with no battles re-run.

| Artifact | Path |
|---|---|
| Per-run win rates | `results/<run_id>/eval.csv` |
| Aggregated table (mean ± std over seeds) | `results/summary.csv` |
| Pairwise matrix | `results/cross_evaluation.csv` |
| Learning curves (raw) | `results/<run_id>/monitor/*.monitor.csv` |
| Figures | `report/figures/*.png` |

33 runs (11 cells × 3 seeds), 300k steps each, 1,500 evaluation battles per run.
Full tables in [report/RESULTS.md](report/RESULTS.md).

**Trained weights are not in the repository.** `model.zip`, `qtable.pkl`, checkpoints and
TensorBoard logs are regenerated by training and are git-ignored; every run keeps its
`config.yaml`, `meta.json` and CSVs. Anything that *loads* a policy (evaluation, the coach,
`play_vs_agent.py`) needs that run retrained first:
`python -m pokerl.train --config <the run's config> --seed <N>`.

> **For a plain-language walkthrough of the whole project** — what it is, how it works, what
> we found, and what the limitations are — see
> **[report/PROJECT_EXPLAINED.md](report/PROJECT_EXPLAINED.md)**. Written to be read without
> knowledge of poke-env or Stable-Baselines3.

**Headline: win rate vs `SimpleHeuristicsPlayer`**, the discriminating opponent:

| Configuration | Win rate |
|---|---|
| PPO + masking, `v0` | **31.1 ± 2.9** |
| PPO, no masking | 24.7 ± 1.5 |
| PPO + masking, `v1` (289 features) | 26.5 ± 1.6 |
| DQN + masking | 11.9 ± 0.5 |
| A2C + masking | 5.7 ± 2.5 |
| Tabular Q-learning | 1.8 ± 0.5 |

**Axis A — algorithm dominates.** PPO ≫ DQN ≫ A2C ≫ tabular, with gaps far outside the error
bars. Action masking is worth **+6.4 points** against SimpleHeuristics but only +2.0 against
MaxBasePower and +0.6 against Random: masking matters exactly when the opponent is strong
enough to punish a wasted turn.

**Axis B — a richer state hurt at this budget.** `v1` (289 features, 256×256 net) scored
26.5 ± 1.6 against `v0`'s 31.1 ± 2.9. Both were still improving at 300k steps, so the
defensible claim is that `v1` is *less sample-efficient*, not worse in the limit — 24× the
input width and far more parameters on hyperparameters tuned for a 12→64→64 network.

**Axis C — shaping buys reliability, not mean performance.** Sparse, shaped, and aggressive
rewards are indistinguishable *when they learn* (~31%). But sparse **failed completely in 1 of
3 seeds** — flat return across 300k steps and 9,072 episodes — giving 22.3 ± 18.6. The failure
was not entropy collapse: the failed run's policy stayed *more* stochastic (entropy_loss
−1.02 vs −0.66 for a healthy seed), i.e. the critic never bootstrapped a useful value from the
terminal-only signal, so advantages stayed uninformative. Shaping's value here is variance
reduction. A two-seed study would have missed this and reported a null.

**Axis D — the training opponent does not matter.** All four (`random`, `max_power`,
`heuristic`, `mixed`) land within 28.9–32.1, overlapping at one standard deviation. Training
against a uniformly random bot produces an agent as strong as training against the best
scripted one. `v0` encodes nothing about opponent behaviour, so there is nothing for opponent
quality to attach to — though the weakest training opponent does give the widest seed spread
(±4.7).

**No trained agent beats `SimpleHeuristicsPlayer` head-to-head.** In the cross-evaluation the
scripted heuristic wins every pairing against every learned agent (56–79%). A well-designed
heuristic remains a strong baseline at this training budget.

**Pipeline sanity gate** (masked PPO, `v0`, 100k steps, trained vs `RandomPlayer`): 96.5% vs
Random, 64.0% vs MaxBasePower, 20.0% vs SimpleHeuristics. The gate required >80% vs random.

## Live coaching mode

A teaching overlay for the Showdown client: while you play, it shows what a trained agent
would do, how strongly it prefers that, and what in the position drives the preference. It
is advice-only and cannot send a move. See [client/README.md](client/README.md) for the
panel and the other ways to attach it.

```powershell
.\scripts\start_showdown.ps1                                                  # terminal 1
.\.venv\Scripts\python.exe -m pokerl.coach.server --run results\ppo_v1_selfplay_seed0   # terminal 2
.\.venv\Scripts\python.exe scripts\install_coach_client.py                     # once
# then open http://localhost:8000 and start a gen9randombattle
```

Three findings shaped its design.

**It runs on `v1`, not on the higher-scoring `v0`.** `v0`'s 12 features contain nothing about
the bench — no teammate HP, types or matchups — so a `v0` switch recommendation has no grounds
that could be reported. `v1` encodes per-teammate HP, status, types and hazards, and is the
only encoder whose switch advice can be explained at all.

**Forced switches are not decisions.** After a faint, switching is the only legal action.
Counting those inflates the agent's measured switch rate from 9% to 25% and manufactures a
spurious "switches when low on HP" trend, since they all occur at 0% HP.
[scripts/diagnose_policy.py](scripts/diagnose_policy.py) excludes them and the panel labels
them explicitly.

**The 300k-step study agent had no opinion on the switch question.** Over 3,372 genuine
decisions, `ppo_masked_v1_seed0` switches voluntarily 9.0% of the time and its switch rate is
flat in its own HP (5.8–11.8% across every band). The judgement the coach most wants to teach
was not represented in the agent's behaviour, so three coach training arms were run to get
it there.

### Coach training arms

Each is `v1`, 5M steps (16× the study budget), seed 0, launched together by
[scripts/train_coach_arms.ps1](scripts/train_coach_arms.ps1) (~5.1 h each, running
concurrently). Configs are in [configs/coach/](configs/coach/).

| Arm | Change from the `v1` study cell | vs Random | vs MaxBasePower | vs SimpleHeuristics | Voluntary switch rate | Switch rate at <20% HP vs ≥60% HP |
|---|---|---|---|---|---|---|
| `ppo_masked_v1` (study, seed 0) | none, 300k steps | 96.0 | 64.4 | 24.8 | 9.0% | 10.6% vs 8.7% (1.2×) |
| `ppo_v1_long` | 5M steps | 95.6 | 65.6 | 27.4 | 10.7% | 10.7% vs 10.8% (1.0×) |
| `ppo_v1_entropy` | 5M steps, `ent_coef` 0.03 | 96.6 | 60.0 | 28.2 | 12.3% | 13.5% vs 11.5% (1.2×) |
| `ppo_v1_selfplay` | 5M steps, self-play | **97.6** | 65.8 | **31.2** | 8.0% | **14.1% vs 5.9% (2.4×)** |

Win rates are over 500 battles per opponent. Switch statistics come from
[scripts/diagnose_policy.py](scripts/diagnose_policy.py): ~3,400–3,600 genuine decisions over
200 battles vs `SimpleHeuristicsPlayer`, with forced switches excluded. Each arm is one seed,
so gaps of about 3 points are within noise.

**Budget alone did not help much.** At 16× the steps `v1` reached 27.4%, against the study's
26.5 ± 1.6, and its switching stayed flat in HP. The higher entropy bonus did no better.

**Self-play is the only arm that learned switch-or-stay.** It switches 2.4× as often below
20% HP as above 60%, and at 31.2% it is the first `v1` agent to match the `v0` reference
cell (31.1 ± 2.9). Its opponent is a lagging copy of itself, refreshed 20 times over the run. Until
the first snapshot exists, `SimpleHeuristicsPlayer` stands in.

**The same agent got worse at move choice.** In 23.7% of its attacking choices another legal
move was at least 1.5× stronger on base power × type multiplier × STAB. The 300k agent's rate
was 12.5% ([scripts/measure_type_choice.py](scripts/measure_type_choice.py)). Win rate hid
this completely. [report/COACH_FINDINGS.md](report/COACH_FINDINGS.md) has the position that
exposed it and the measurement.

That is why the commands above point the coach at `ppo_v1_selfplay_seed0`. The server's
built-in `--run` default is still the 300k `ppo_masked_v1_seed0`. Trust self-play on
switch-or-stay. Check its move recommendations against the type chart the panel already
prints.

Two follow-ups are recommended but not yet built: flagging type-dominated recommendations
in the panel, and league training (self-play plus the scripted heuristic, which is what
punishes weak moves).

These arms are deliberately kept out of the study matrix. They vary several fields at once,
so folding them in would break the "exactly one field differs from the reference cell"
property that makes the comparisons above attributable.

## Implementation notes

Things that are non-obvious, and were found the hard way.

**Seeding breaks poke-env's usernames.** poke-env generates account names with the `random`
module. Seeding the global RNG for reproducibility makes those names *identical on every run*,
so a new process reconnects under a name the previous run's socket still holds and battles
never close out — surfacing much later as `Can not reset player's battles while they are still
running`. [`_unique_accounts`](src/pokerl/env/battle_env.py) mints names from `uuid4`
(`os.urandom`-backed, immune to `random.seed`). Reproducibility must cover the agent's
decisions, not its network identity.

**poke-env already supplies the action mask.** `PokeEnv.__setattr__` intercepts assignment to
`observation_spaces` and wraps each entry into `Dict({"observation": …, "action_mask": …})`,
populating the mask every step. `embed_battle` must therefore return the *raw* vector;
returning a dict nests the space twice and SB3 rejects it.

**DQN needs masking in three places, not one.** There is no `MaskableDQN` in SB3 or
sb3-contrib, so [masked_dqn.py](src/pokerl/policies/masked_dqn.py) provides one. Masking the
Q-network covers both action selection *and* the bootstrapped target (an unmasked target lets
the agent bootstrap from moves it can never take). Separately, the epsilon-greedy branch and
the `learning_starts` warmup both sample raw from the 26-action space — the warmup bypasses
`predict()` entirely via `_sample_action`, and missing it fills the replay buffer almost
entirely with illegal transitions.

**Some moves have no `priority`.** poke-env synthesizes data entries for the pseudo-moves
`recharge` (the forced turn after Hyper Beam / Giga Impact) and `fight`, containing only
`pp`, `type`, `category`, and `accuracy`. `Move.priority` indexes straight into that entry, so
it raises `KeyError` — inside a `SubprocVecEnv` worker, which the parent then reports only as
`EOFError` on a broken pipe, hundreds of thousands of steps into a run. All raw move
properties therefore go through [`_move_attr`](src/pokerl/env/encoders.py). Only `v1` reads
`priority`, which is why `v0` was unaffected.

**The environment runs with `strict=False`, because of the *opponent*.**
`SingleAgentWrapper.step` converts the opponent's chosen order back into an action with
`[m.id for m in mvs].index(order.order.id)`. `SimpleHeuristicsPlayer` can select a move that
is momentarily absent from `available_moves` — observed as `ValueError: 'hydropump' is not in
list` — which is a poke-env inconsistency that the agent neither causes nor controls. Under
`strict=True` it terminates the run; under `strict=False` poke-env substitutes a default
order and the battle continues. Strict mode was originally kept on to catch bugs in our own
action encoding, but the agent's actions are mask-verified, so it bought little and cost
whole 13-minute runs.

**Don't retry a failed `reset`.** `PokeEnv.reset` forfeits and drains both agents' battle
queues *before* the call that can raise, so a second attempt re-enters with those queues
already consumed and can hang. Wait for the battle to settle beforehand instead.

**Windows + `SubprocVecEnv`.** Every entrypoint sits behind `if __name__ == "__main__":`.
Without it each spawned child re-imports the module and spawns its own children, recursively.

**The GPU is not the bottleneck.** The Node.js simulator is. poke-env's own example sets
`device="cpu"` because a 64×64 MLP is faster on CPU than paying transfer overhead; parallel
environments matter far more than CUDA. `v1` (289 features, 256×256 net) is the only
configuration where the GPU is worth benchmarking. PyPI's Windows torch wheel is CPU-only —
see [requirements.txt](requirements.txt) for the CUDA index URL. SB3 falls back to CPU
automatically if `device: cuda` is requested without CUDA available.

**Tuning throughput.** Measured mid-study on the reference hardware (Ryzen 7 5800H, 8C/16T),
during a run with `num_envs: 6`:

| Process | CPU (% of one core) |
|---|---|
| learner (parent python) | **709%** |
| each of 6 env workers | 13–17% |
| Showdown main worker (node) | 60% |
| whole machine | 62.9% of 16 threads |

Two lessons. First, the env workers are **latency-bound, not compute-bound** — they sit
blocked on websocket round-trips, so the fix for throughput is more concurrency, not more
compute. Second, the learner burned seven cores on a 64×64 MLP: for tensors that small,
thread synchronisation costs more than the arithmetic, and it starves the workers that are
actually on the critical path.

The tuned configuration, in order of effect:

1. **`torch_threads: 1`** in the config (or `--torch-threads 1`). Frees ~6 cores and is
   typically *faster* per run, not just cheaper.
2. **Raise `num_envs`** to 12–16. Workers at 15% CPU have plenty of headroom.
3. **`workers: 2`** (or more) in `pokemon-showdown/config.js`. Node's event loop is
   single-threaded, so one Showdown worker saturates at roughly 1.6× the observed battle
   rate — it becomes the ceiling once the first two changes land.

None of this changes results, only wall-clock time. `torch_threads` defaults to `0`
(torch's own default) so that runs predating this measurement stay comparable.

**Self-play snapshots need a new filename every time.** The learner publishes its policy for
the `snapshot` opponent to load, and every env worker reloads the moment a new one appears.
On Windows, overwriting a zip that a worker has open fails with `PermissionError`, which
killed a two-worker smoke run on its second write. `SnapshotCallback` in
[train.py](src/pokerl/train.py) therefore writes `opponent_<step>.zip` under
`results/_snapshot/`, readers take the highest number, and old files are pruned only when
nothing holds them.

**The masked policy has to set the mask in `get_distribution` too.** Training and `predict()`
go through `forward`/`_predict`, which set the mask. The coach reads the action
*distribution* instead, and without the override in
[masked_ac.py](src/pokerl/policies/masked_ac.py) that call reuses whatever mask the previous
call left behind. That silently puts probability on illegal actions.

**Concurrent runs are limited by RAM, not CPU.** Three arms at 8 envs each is 24 env
subprocesses, each carrying its own torch and poke-env, and that exhausted 15.4 GB. One arm
died on a 3.39 MiB allocation. The coach arms therefore use 6 envs. All arms must share the
value, because `n_steps // num_envs` sets the rollout length.

**`gen9randombattle` is high-variance.** Random teams every battle mean noisy curves. This is
why 500 evaluation battles and 3 seeds are required, not optional. Battle outcomes are not
bit-reproducible in any case: the Showdown server's RNG for damage rolls, criticals, accuracy,
and team generation is not seeded from Python.
